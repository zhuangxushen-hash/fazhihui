线索「发合同」与「转化为案件」合并方案

代码核对版 · 结论：两者业务语义一致（发合同签约 = 转化案件），但当前存在两条独立入口 + 两套不对称建案逻辑。建议收敛为单入口，并统一建案内核补齐差异。

你的判断成立。 业务上「签了委托合同，案件即成立」，所以「发合同」和「转案件」是同一件事。
代码现状：fadada 模块已实现新流程「线索 → 发合同(签约) → 签约完成自动生成案件」，而 lead.service.convertToCase 仍保留旧入口「线索直接建案」，二者并存、逻辑重复且不一致。

关键不一致（合并时必须解决）：
  • 路径 C（新流程）建案时缺少利冲检索与缺少应收台账，而路径 A 有。即：经发合同签约自动生成的案件，不会被利冲挂起、也不会产生应收台账 —— 合规与财务闭环缺失。
  • 路径 A 建案不关联合同（当时无合同）；路径 C 关联合同。合并后应统一「有合同」。
  • 路径 B 有「谈案SOP强制节点」校验，路径 A/C 没有。合并时需统一合规门槛。

二、合并目标架构

合并后：线索「转案件」唯一入口 = 发合同（launch-from-lead）→ 签署 → 公共建案内核。旧 convertToCase 改为复用同一内核（或下线）。内核统一负责利冲、客户档案、应收台账、建案、回写合同/线索，消除不一致。

三、合并方案（推荐）

原则：① 收敛入口 —— 线索「转案件」统一走发合同流程；② 统一内核 —— 抽一个公共建案函数，所有路径复用；③ 补齐缺口 —— 利冲、应收台账、SOP 校验在统一内核内一致执行。

步骤 1 · 抽出公共建案内核 buildCaseFromLead

新建 / 或放进 fadada.service.ts 或 case.service.ts：
async buildCaseFromLead(ctx: { lead, contract?, caseFields, supplement })
职责（一次性封装，替换三处重复逻辑）：
  • 利冲检索 conflictCheckService.check → 命中置 approval_status=conflict_hold（补齐路径 C 缺口）
  • 按手机号查找/建档客户档案 clientProfile
  • 按 fee_amount/service_fee 生成应收台账 Receivable（补齐路径 C 缺口）
  • 建案件（案件号按组织规则；status 取组织默认；stage=intake）
  • 回写：contract.case_id, stage=signed · lead.conversion_status=converted, case_id

步骤 2 · 新流程 generateCaseFromContract 改为调用内核

文件 fadada.service.ts:1447。
将现有「手动建案 + 建客户档案」替换为 buildCaseFromLead，移除重复映射（合同→案件字段映射保留在外层 caseFields 入参）。顺带补齐利冲与应收台账。

步骤 3 · 旧 convertToCase（线索）改造

文件 lead.service.ts:169。
方案二选一（见下「待确认」）：
  • 方案 X（推荐·最小改动）：保留 POST /leads/:id/convert 作为「无合同快速建案」，内部改为调用 buildCaseFromLead({ lead, contract:null })，自动获得利冲/应收台账一致性。
  • 方案 Y（彻底合并）：下线 convertToCase 入口，前端线索页「转案件」按钮改为打开发合同 launch-from-lead（已有 LeadSignLaunch 组件）。
无论 X/Y，旧路径都不再自写建案逻辑。

五、风险与回滚

  • 数据缺口 历史已通过路径 C 生成的案件缺应收台账：合并后新案件不再缺，但存量需跑一次补数脚本（按 contract.amount 补应收台账、按当事人补利冲记录）。
  • 合规升级 给发合同流程补 SOP 强制节点/利冲后，已存在「未过SOP就发合同」的数据需评估是否回溯校验。
  • 回滚 内核改动用事务包裹；若下线 convertToCase，保留方法体为 deprecated 别名一段时间再删，便于灰度。
  • 幂等 generateCaseFromContract 已有 if(contract.case_id) 幂等保护，复用内核不会重复建案。
