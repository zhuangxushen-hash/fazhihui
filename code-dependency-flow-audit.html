5.2 🟠 缺失外键 / 关联字段

  • Case 的 client_id/lead_id/contract_id/assignee_lawyer_id 全是裸 @Column({nullable:true})，无 @ManyToOne 约束（case.entity.ts:24-31/169）；仅 assignee_lawyer 有真关系。→ 逻辑关联、无 DB 外键、无级联，统计易失真。
  • Case.lead_id 与 related_lead_id 重复（:30 与 :174）语义重叠。
  • Lead → Client 无外键：Lead 实体无 client_id（仅 case_id:77），转客户靠手工。
  • ComplaintTicket.case_id / client_id 裸 varchar 可空（complaint-ticket.entity.ts:83-95），无约束。
  • Receivable 仅 case_id 裸列，无 client_id（receivable.entity.ts:26），与案件客户无法联动。

5.3 重复 / 分散的枚举

① 案件状态：后端枚举 + 裸 varchar(stage/change_status) + DB 可配置 caseStatus API 三套；② 投诉类型：types 枚举 × 实体 TicketComplaintType × 前端 api 三处；③ 渠道类：LeadSource/AdChannel/AdPlatform/TicketSourceChannel/ChannelTracking 各自为政。

5.4 最该补的 3 个数据模型缺口

  1. Case.client_id/lead_id/contract_id 改真 @ManyToOne 外键（含级联），合并 lead_id 与 related_lead_id 重复字段。
  2. Lead 增 client_id 外键 + Client/Case 增"所属销售 owner_sales_id"，打通销售业绩归因闭环。
  3. 收敛"收款状态"为单一枚举，并在 Case 增"分润已发放 disbursed 标记"字段关联 profit-share 状态。

⑦ 建议行动路线

第一步（一期上线前，1–2 天，纯代码）：先把 P0 的"阻断性"项打掉——RBAC deny-by-default、C端支付/建案回流、/upload 端点、分润真触发、非 HTTP 异常改造。这几项不修，一期 C 端付费闭环与系统安全都不成立。
第二步（一期稳定后，3–5 天）：做 P1 数据治理——外键约束、枚举统一、收款写 BusinessFund、利润口径统一、事件化解耦。否则数据会逐渐失真、统计报表不可信。
第三步（二三期）：按 PRD 分期接外部服务，并把 P2 的 mock 模块从 app.module 移除或页面明确标"演示版"，避免对外承诺假能力。

说明：本报告所有结论均来自对 backend/src 与 frontend/src 的静态扫描与多路探查代理交叉核验，未运行构建。落地任意一项前建议本地 cd backend && npx tsc --noEmit 与 cd frontend && npm run build 终验。
