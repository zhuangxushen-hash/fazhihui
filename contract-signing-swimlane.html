发合同 → 建案 → 利冲 / 应收 / 分润　泳道图

泳道 = 角色 / 系统；节点自上而下 = 时间顺序；每个节点底部「↘ 交还」表示跨泳道流转。基于真实代码：fadada.service.ts commission.service.ts。所有判断与报错均标注源码行号。
判断分支（if / 状态切换） 报错 / 阻断（throw / 回退） 静默吞错（catch 后继续，无人知晓）

① 销售 / 谈案律师
（B端）

S1 · 发起发合同
填写合同信息并发起
在发合同页填写客户/案由/收费/主体，并提交「生成案件用」的补充信息（案由、对方当事人、承办律师、协办、收费方式…），调用 launchSignFromLead。
⚠ 判断：线索是否存在？ 否 → 报错「线索不存在」并阻断（fadada:1348）。
静默：合同号按编号规则生成失败 → 回退随机编号，无提示（:1361）。
↘ 交还【法大大电子签】创建签署任务
S2 · 生成合同 PDF + 建记录
建 Contract + 签约合规记录
生成合同 PDF、保存 Contract（stage=signing）、保存 SigningCompliance（status=pending），再调用 createSignTaskFromTemplate 发起法大大签署任务。
报错：法大大文档上传/处理失败 → throw「法大大文档上传地址获取失败 / 文档处理失败」（:1733 / :1742）。
静默：发起签署任务整体失败时 → 删除刚建的 Contract 与 SigningCompliance 脏数据，再向上 throw（:1442-1444）。

② 法大大电子签
（第三方·当前为 MOCK）

S3 · 返回签署链接
发起签署任务成功
法大大返回 signTaskId / actorId / signUrl（当前接入为 mock，链接非真实签署页）。
↘ 交还【客户（C端）】实名 + 签署
S4 · 推送签署回调
签署完成事件 sign-task-finished
客户签署完成后，法大大回调 handleCallback。
⚠ 判断：eventId 是否缺失？ 缺失 → 直接 return {handled:false}，事件被丢弃，后续什么都不做（:1629）。
⚠ 判断：按 fadada_sign_task_id 能否找到 SigningCompliance 记录？找不到 → 无动作（:1682）。
⚠ 判断：回调事件类型？ sign-task-finished→SIGNED；sign-task-signed→REVIEWING；rejected/canceled/abolish→REJECTED（:1686-1693）。
↘ 交还【回调 / Fadada 模块】校验并触发建案

③ 客户
（C端）

S5 · 收链接 + 实名 + 签署
客户完成签署
客户点击签署链接，先做实名认证（user-authorize），再签署。
⚠ 判断：实名是否成功？ 否 → signing.verify_status=failed（:1665）。
⚠ 判断：签署是否完成/被拒？ 被拒/撤销 → 案件永不生成。
↘ 交还【法大大电子签】推送回调

④ 回调 / Fadada 模块
（后端）

S6 · 回调校验
判定是否触发建案
在 handleCallback 内判断是否自动建案。
⚠ 判断：status===SIGNED 且 尚无 case_id 且 有 contract_id？ 是 → 调用 generateCaseFromContract（:1697-1703）。
↘ 交还【案件模块】生成案件
S10 · 回写 + 短信
建案结果回写
建案成功后回写 signing.case_id。
⚠ 静默吞错（高危）：若 generateCaseFromContract 整体抛错（如建档/建案失败）→ 仅 logger.error，签约记录已 SIGNED 但 case_id 为空 → 「有签约、无案件」且无人知晓（:1708-1713）。
判断：status===SIGNED 且 已有 case_id → 触发收案短信（失败不影响主流程）。
↘ 交还【案件模块】回写合同 /【线索】回写转化

⑤ 案件模块
（Case）

S7 · 生成案件
generateCaseFromContract
合同字段 + 补充信息填入案件；按手机号自动建档客户（保证 C 端可见）。
静默：合同不存在 → warn 后 return null，不报错（:1460）。
静默：已建过案件 → 幂等返回旧案件（:1464）。
静默：case_supplement JSON 解析失败 → 补空对象（:1473）。
静默：案件号生成失败 → 回退随机编号（:1509）。
静默：组织默认状态读取失败 → 回退 pending_assign（:1521）。
↘ 交还【利冲模块】利益冲突检索
↘ 交还【财务模块】建应收 / 触发分润
↘ 交还【④ 回调】回写合同 + 线索转化
S12 · 回写合同 / 线索
建案收尾
回写 contract（stage=signed, case_id）、回写 lead（conversion_status=converted）。

⑥ 利冲模块
（Compliance）

S8 · 利益冲突检索
conflictCheckService.check
签约建案即做利冲校验。
⚠ 判断：check_result==='conflict'？ 是 → 仅把案件 approval_status 置为 conflict_hold，不阻断建案，留痕供合规复核（:1570）。
⚠ 静默吞错（高危）：利冲查询本身抛错 → 仅 logger.error，案件照常建、利冲等于没做、无人知晓（:1573-1575）。

⑦ 财务模块
（Finance）

S9 · 建应收台账
签约即建 receivable
按 fee_amount 建应收（received=0, pending=全额, status=PENDING），财务立即可见待收。
⚠ 静默吞错（高危）：建应收抛错 → 仅 logger.error → 「有案件、无应收」账实不符（:1590-1592）。
S11 · 触发分润
checkAndTriggerCommission
（签约即算）
建案后调用分润检查，期望「签约即算分润」。
⚠ 判断①：case.status !== CLOSED？ 签约时案件是 pending_assign → 永远成立 → 直接 skipped（commission:323）。
⚠ 判断②：应收 status !== COMPLETED？ 刚建的应收是 PENDING → 也 skipped（:325）。
⚠ 判断③：已存在分润记录 → skipped。
结论：签约时调用 永远是死代码，分润实际要靠「结案 / 全款到账」时才真正触发（同方法在 case.service:766/989、finance.service:202 被调用）。
⚠ 静默吞错：分润调用整体抛错 → 仅 logger.error（:1597-1599）。

一、时序总览（按阶段）

阶段泳道动作关键判断 / 报错
S1①销售发起发合同线索不存在 → 报错阻断；合同号失败→静默回退
S2①销售建合同+签约记录+发起法大大法大大上传/处理失败 → throw；整体失败→删脏数据再throw
S3②法大大返回签署链接当前为 MOCK
S4③客户实名+签署实名失败→verify_status=failed；被拒/撤销→不建案
S5②法大大推送 sign-task-finished 回调eventId缺失→丢弃；找不到signing→无动作；按事件类型置状态
S6④回调判定是否建案SIGNED 且无 case_id 且有 contract_id → 触发建案
S7⑤案件generateCaseFromContract 建案合同不存在/已建/JSON错/编号错/默认状态错 → 均静默回退
S8⑥利冲利益冲突检索命中→conflict_hold不阻断；查错→静默吞错
S9⑦财务签约即建应收建应收失败→静默吞错→有案无应收
S11⑦财务签约即算分润因 status≠CLOSED + 应收≠COMPLETED → 永远 skipped（死代码）
S10④回调回写 case_id + 短信建案整体抛错→静默吞错→有签约无案件
S12⑤案件回写合同+线索转化正常收尾

二、最危险的「静默吞错」汇总（比报错更危险）

#环节吞错后后果代码
1建案整体失败签已完成但 case_id 空 → 有签约、无案件，财务/办案全断，且无人发现fadada:1708
2利冲查询失败案件照常建，利益冲突未检，合规风险漏检fadada:1573
3建应收失败有案件、无应收 → 财务账实不符，后续分润也无法触发fadada:1590
4分润调用失败分润未生成，律师拿不到钱，无提示fadada:1597
5分润条件永不满足签约即算分润是死代码，实际靠结案/全款触发，逻辑与注释矛盾commission:323/325
6合同号/编号/默认状态读取失败回退随机编号或默认状态，数据不规范但能跑fadada:1361/1509/1521
📌 这 4 个「建案 + 利冲 + 应收 + 分润」是各自独立 save、各自 try/catch，没有数据库事务包裹。任一中间步失败，前面已写入的数据不会回滚，最终状态「半成功」——这是本链路最该修的根因。

三、给研发的修复优先级（纯代码，一期可补）

优先级事项做法
P0建案纳入事务 / 明确失败补偿把 S7–S11 的建案+利冲+应收+分润放进一个 DB 事务，或加「建案失败补偿任务」，杜绝「半成功」状态；至少把静默 catch 改成告警通知而非仅 logger。
P0分润触发逻辑对齐签约即算分润的条件（status=CLOSED & 应收 COMPLETED）永远不满足 → 要么改触发口径（如签约即按 fee_amount 预生成待发放分润），要么删掉这处死代码、统一由结案/全款触发，并修正注释。
P1利冲失败升级为阻断或强告警利冲是合规红线，查询失败不应静默放行；建议失败即挂起案件待人工复核，而非默默跳过。
P1回调事件丢弃补救eventId 缺失 / 找不到 signing 时，应入「待处理回调队列」并告警，避免签署完成却无动作。
P2法大大 MOCK 替换当前为演示，正式上线需接真实法大大签署 + 验签，否则签署状态不可信。
说明：本图不含 C 端支付/付款（按你的要求本期不做）。整条链路的「发起 → 签署 → 建案 → 财务联动」逻辑是通的，但「建案 + 利冲 + 应收 + 分润」四步缺乏事务与失败告警，是上线前必须加固的部分。
