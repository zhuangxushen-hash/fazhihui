1线索（Lead）生命周期

核心文件：lead/lead.service.ts · lead/invite-task.service.ts · 实体 lead.entity.ts

① 线索创建 create()

项内容
前置条件手机号合法；同手机号 7 天内已存在线索 → 不入新表，直接返回旧线索（去重，见代码 created_at > now-7d）。
后置动作写入 Lead；随后异步 自动匹配分配规则（matchAndAssign，异常静默不阻断）。

② 分配销售 assignSales()

项内容
前置条件线索存在。
后置动作assign_sales_id 赋值，status = PENDING_FOLLOW（待跟进）。

③ 添加跟进 createFollowUp()

项内容
前置条件线索存在。
后置动作写入跟进记录；status = FOLLOWING（跟进中），follow_up_time = now。

④ 公海回流 autoRecycle()

项内容
前置条件status = PENDING_FOLLOW 且 created_at 早于阈值（默认 24 小时）。
后置动作批量置 status = LOST（即回流并标记为流失）。
⚠ 文档与代码不一致：需求文档（5.3 / 13.7）写的是「72 小时无跟进回流公海」，而 autoRecycle(timeoutHours=24) 默认参数与「线索分配后 72 小时」口径不同。若以代码为准，待跟进线索 24 小时即判流失，需向产品确认是否要统一为 72h。

⑤ 线索编辑 update()

项内容
前置条件线索存在；若改手机号，必须 未被其他线索占用（ConflictException 拦截「该手机号已存在其他线索」）。
后置动作仅 patch 传入字段，避免误清空。

2邀约（InviteTask）与「到所自动建商机」

核心文件：lead/invite-task.service.ts

① 创建邀约 createInviteTask()

项内容
前置条件线索存在；操作人角色 ∈ {SALES, ORG_ADMIN, SUPER_ADMIN}。
后置动作写入 InviteTask；若 result=SUCCESS → 线索 status=INVITING（邀约中）；若 result=INVALID → 线索 LOST。

② 更新到所 updateTaskStatus(ARRIVED)

项内容
前置条件任务存在且 inviter_id == 当前用户。
后置动作线索 status=NEGOTIATING（谈案中）；自动预建商机（createOpportunity，若线索已有商机则跳过；异常静默）。NOT_ARRIVED → 线索回到 FOLLOWING。
⚠ 文档缺失：需求文档未明确「邀约到所 → 自动预建商机」这条自动化，代码（13.8 缺口3）已实现，是本产品拉通谈案域的关键衔接点。

③ 录音上传 uploadRecording()

项内容
后置动作保存录音 URL；若带转写文本则异步触发谈案 AI 质检（runTalkQualityCheck，异常静默）。

3商机（Opportunity）谈案成交流程

核心文件：lead/opportunity.service.ts · lead/talk-sop.service.ts

① 创建商机 createOpportunity()

项内容
前置条件所属线索存在；该线索尚未创建过商机（BadRequestException: 该线索已创建商机，保障一对一）。
后置动作创建商机 stage=FIRST_CONTACT（初步沟通）、status=ACTIVE；写阶段变更日志；线索 status=NEGOTIATING。

② 阶段推进 updateStage()

项内容
前置条件商机存在；SALES 仅能操作自己的商机（negotiator_id == userId）。
后置动作更新 stage（初步沟通→方案设计→报价→签约）；写阶段日志。报价项变更后自动重算 quote_amount。

③ 签约转化 convertToCase()（关键闭环）

项内容
前置条件
  • 商机存在、线索存在；
  • 商机 stage != SIGNED（已签约则报错）；
  • 谈案 SOP 强制节点全部完成（checkRequiredNodesCompleted，未完成则报「以下强制节点未完成」）。
后置动作 事务内：新建案件（status=PENDING_ASSIGN，带回 lead_id / opportunity_id）；商机 stage=SIGNED、status=COMPLETED、conversion_time；线索 status=PENDING_SIGN、conversion_status=converted。
⚠ 文档缺失：文档把「报价→签约→收款」画成独立节点，但代码里「签约转化」必须过 谈案 SOP 强制节点 这道卡口，这是防止违规签约的实质校验，务必写入流程。

④ 标记为流失 markAsLost()

项内容
前置条件商机存在且权限匹配。
后置动作商机 stage=LOST、status=COMPLETED；线索 status=LOST。

4案件（Case）办案交付流程

核心文件：case/case.service.ts · 实体 case.entity.ts

① 新建案件 create()

项内容
前置条件必须带 organization_id，否则拒绝。
后置动作 事务内：生成案件编号（AJ-YYYYMMDD-XXXX 或组织编号规则）；风险等级自动评级（金额>50万 / 期限<15天 / 刑事·行政案由 → medium/high）；利冲检索（命中则 approval_status=conflict_hold）。
事务外（异常静默）：类案匹配结果追加到描述；办案 SOP 自动生成。

② 分配律师 assignLawyer()

项内容
前置条件案件存在。
后置动作assignee_lawyer_id 赋值，status=PROCESSING（办理中）；若有关联合同则回写合同主办律师。

③ 审批流 submitApproval / approve / reject

项内容
前置条件案件存在。
后置动作approval_status 在 pending↔approved/rejected 间流转；若原 stage=intake，审批通过自动转 processing。

④ 结案 closeCase()（关键闭环）

项内容
前置条件案件存在（通常经 updateStatus(CLOSED) 进入）。
后置动作 事务内：status=CLOSED；若合同处于 signed/performing → 合同 stage=completed；若应收 已收 ≥ 应收总额 → 合同 is_settled=true；触发分润检查（异常静默）。
事务外：触发客户评价（C 端）、自动生成结案报告文书、推送 C 端结案短信。

⑤ 结案归档 archiveCase()

项内容
前置条件案件存在；通常已结案。
后置动作stage=closed 并生成归档编号；同样执行「合同完结 + 应收结清 + 分润触发」联动；推送办结短信。批量归档 batchArchive 逐个复用、单失败计数不中断。

⑥ 变更 / 解约 / 作废

项内容
后置动作changeCase → change_status=changed；terminateCase → status=terminated；voidCase → status=voided。三者均记录原因/操作人/时间并写审计日志。
⚠ 文档与代码不一致：文档案件状态只有「待受理/办理中/已结案/已归档」，但代码实际使用多维字段组合：status(PENDING_ASSIGN/PROCESSING/CLOSED/TERMINATED/VOIDED)、stage(intake/processing/closing/closed)、approval_status(pending/approved/rejected/conflict_hold)、change_status。建议以代码状态机为准重写文档枚举。

环节前置条件后置动作

6收款、应收账款与分润结算

核心文件：finance/finance.service.ts · finance/commission.service.ts · finance/receivable.entity.ts

① 开票 / 登记收款（应收台账来源）

线索/商机转案件时已自动预建应收台账（Receivable，status=PENDING，contract_amount=fee）。后续通过 receivables/:id/record-payment 登记。

② 登记收款 recordPayment()（关键闭环）

项内容
前置条件应收台账存在；amount > 0（否则 BadRequestException）。
后置动作 事务内：写 PaymentRecord(PAID)；累加 received_amount，重算 pending_amount； 若 已收 ≥ 应收 → 应收 status=COMPLETED； 回写案件 fee_collected / settled_amount； 应收变 COMPLETED → 自动触发分润检查。

③ 分润计算 calculateCommission / checkAndTriggerCommission()

项内容
前置条件 案件必须已结案（status == CLOSED，否则「案件未结案，无法计算分润」）； 且应收台账已结清（ReceivableStatus.COMPLETED，否则「款项未结清」）。
后置动作按「角色类型 + 案由」匹配分润规则（固定/百分比/阶梯），生成 CommissionRecord（待结算）；markPaid() 后状态转 PAID。
⚠ 文档缺失：「收款 → 分润」是自动串联的（全款到账即触发），文档只在 13.7.3 提到，但未在财务章节列明触发条件；建议补进 8.9 分润配置说明。

7客户端（C 端）关键衔接

核心文件：client/client.service.ts · fadada/*

  • AI 咨询转人工：C 端识别复杂问题 → 按手机号/姓名 自动建线索（来源关键词=AI咨询转人工），7 天去重，复用自动分配规则。
  • 在线签约：法大大电子签（实名三要素 + 人脸/短信核验）→ 签署任务 → 状态回调（pending/verified/signed）。
  • 在线支付：微信/支付宝/银行卡，支付成功回调触发电子发票开具。
  • 结案评价 / 我的归档：结案后 C 端可评价（联动律师评级中心），并可查询/下载归档卷宗。

9核心闭环（一句话总结）

  • 线索→案件：POST /leads/:id/convert 事务内自动做利冲检索 + 客户档案 + 应收台账。
  • 商机→案件：POST /opportunities/:id/convert-to-case 校验 SOP 强制节点后签约，建案并回写线索。
  • 收款→分润：receivables/:id/record-payment 全款到账触发 checkAndTriggerCommission。
  • 案件→归档：POST /cases/:id/archive 联动归档卷宗 + 合同完结 + 分润 + 客户短信。
  • 客户→服务：C 端评价联动律师评级；投诉含处理与升级；舆情/合规→站内推送。
