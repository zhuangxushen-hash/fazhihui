① 线索生命周期

角色：营销岗 / 销售 / 谈案律师。入口：广告 webhook、手工录入、活码。

步骤1 · webhook 写入线索
◈ 判断：平台配置/签名缺失 → 抛 验签失败；!data.phone → 抛 线索缺少手机号；resolveOrgId 为 null → 抛 无法识别线索归属组织
静默：7 天内同手机号 → 直接返回旧线索、不报错（去重）
步骤2 · 手工 createLead
◈ 判断：前端 phone 必填；后端未做 phone 校验（空值靠数据库报错）；客户字段非必填
静默：matchAndAssign 自动分配包 try/catch 吞错（分配失败不提示）
步骤3 · 活码 channel-tracking
⚠ 活码只做扫码计数，从不写 Lead → 所以"来源渠道 source_channel"永远不填，线索归因丢失（来源线索实际走 webhook / 手工录入）
步骤4 · 线索状态机 LeadStatus
◈ 判断：手动切（updateStatus/assignSales→PENDING_FOLLOW/createFollowUp→FOLLOWING）；自动切（邀约 SUCCESS→INVITING、到所→NEGOTIATING、签约→PENDING_SIGN、流失→LOST）
静默：updateStatus 无枚举校验 → 任意脏值可写入、不阻断
步骤5 · 进公海池（Cron 凌晨1点 / 手动）
◈ 判断（手动 manualRecycle）：线索不存在 → 404；未分配 → BadRequest 该线索未分配，无法释放；非本人 → Forbidden 只能释放自己负责的线索
自动：超时(被跟进超7天)且有负责人 → 入池+LOST；已在池 → warn 跳过
步骤6 · 认领 claim
◈ 判断：记录不存在 → 404 公海池记录不存在；跨组织 → 403；status≠AVAILABLE → BadRequest 该线索已被领取或已废弃；take_count≥3 → 置 DISCARDED + BadRequest 该线索已达到最大领取次数，已被废弃
静默：成功通知包 try/catch（通知失败不提示）
步骤7 · 再分配 reassignLead
⚠ 死代码：方法存在但无 controller 路由、无前端调用 → 销售之间无法在系统里转派线索（只能线下口头说）
步骤8 · 邀约 invite-task
◈ 判断：线索不存在 → 404；用户不存在 → 404；角色非 sales/admin → Forbidden 只有邀约岗和管理员可以创建邀约任务
◈ 结果分支：SUCCESS→INVITING；INVALID→LOST；其余 PENDING
无外呼：仅建记录 + 站内 notify（"成功/失败"对用户=状态变更+通知，无真实外呼回执）；录音质检 try/catch 吞错
步骤9 · 谈案 talk / talk-sop
◈ 判断（到所）：ARRIVED→NEGOTIATING + 建商机（已存在 → BadRequest 该线索已创建商机，但调用处 catch 静默）；NOT_ARRIVED→FOLLOWING
◈ 谈案结果：通过 = 转案件(lead→PENDING_SIGN)；不通过 = 标记流失(→LOST)；待定 = 停留 NEGOTIATING
阻断（转案件）：已签约 → BadRequest 该商机已签约；强制 SOP 节点未完成 → BadRequest 以下强制节点未完成：…
质检：关键词命中 REJECT，但整段 try/catch 吞掉（质检异常无感知）

② 发合同 → 签署 → 建案 → 利冲 → 应收 → 分润（核心链路）

角色：律师/助理。这是全系统最复杂、隐患最多的链路。补偿动作（利冲/应收/分润）全部被"静默吞错"，且分润触发条件结构性不满足。

步骤0 · 发合同入口 launchSignFromLead
◈ 判断：仅校验 !lead → Error 线索不存在；无 case_id/客户必填校验
合同号按编号规则生成失败 → catch 回退随机号；clientName 按 corp/person 兜底
步骤1-2 · 建合同记录 + 建签约合规记录
合同金额缺失 → 0 静默入库；签约合规记录 case_id 存空串（仅绑 lead/contract）
步骤3 · 发起签署 createSignTaskFromTemplate
◈ 判断：!enabled → 法大大电子签未启用；mode==='mock' → 返回本地模拟链接（不走真实签署）
prod 下：模板/参与方异常冒泡；无 signTaskId → 法大大模板签署任务创建失败：…
预填字段逐字段 try 容错，单字段失败仅 warn 跳过；prod 返回 signUrl 为空（真实链接后续再取）
步骤4 · 发起失败清理
catch(e)：先 remove(signing) 再 remove(contract)（均静默），然后 throw e → 前端收到异常（HTTP 500 / 业务错误）
步骤5 · 客户签署完成回调 handleCallback
先 res.json({msg:'success'}) 再异步处理；任何异常仍返回 success（防法大大重试风暴）
步骤6 · 回调验签 verifyCallbackSign
◈ 判断：未配置 AppSecret → 返回 null（跳过）；缺 sign/timestamp → false；HMAC 不等 → false
⚠ 验签失败（false）→ controller 直接 return，事件被静默丢弃、不重试（可能丢签署结果）；返回 null 反而放行。另：verifyCallbackToken 是死代码从未调用
步骤7 · 签署完成状态分支
◈ 判断：sign-task-finished → SIGNED；sign-task-signed → REVIEWING；拒绝/撤销 → REJECTED
◈ 触发建案条件：status===SIGNED && !case_id && contract_id
步骤8 · 建案 generateCaseFromContract
◈ 判断：!contract → return null 静默；已 case_id → 幂等返回（防重复建案）
case_supplement JSON 解析失败 → catch 置空；无手机号 → clientId=null 静默；编号生成失败 → catch 回退 AJ-随机；默认状态读取失败 → 回退 pending_assign
建案 save 失败 → 抛出异常，被步骤7 的 catch 记录日志，签名记录不写 case_id
步骤9 · 利益冲突检索 conflictCheckService.check
◈ 判断：当事人与对方同命中 → conflict；仅一方 → warning；否则 clear
⚠ 命中冲突仅置 approval_status:'conflict_hold'（留痕），不阻断建案；利冲异常仅 logger.error，案件已建 → 利冲失败无人知
步骤10 · 应收台账 receivable save
◈ 判断：feeAmount=0 也建 PENDING 应收；客户缺失不校验（案件已有 client 关联）
⚠ 应收保存异常仅 logger.error → 应收漏建，但案件照常生成 → 财务账实不符
步骤11 · 分润触发 checkAndTriggerCommission
◈ 判断：status!==CLOSED → skipped；receivable!==COMPLETED → skipped；已存在 → skipped
🔴 签约时案件为 pending_assign（非 CLOSED）、应收为 PENDING（非 COMPLETED）→ 永远 skipped，分润永不在签约触发（死代码分支）；异常仅 failed++ 静默
步骤12 · 回写
更新 contract 为 signed + case_id；线索转 converted（无论利冲/应收/分润是否成功）
步骤13 · 事务性（架构隐患）
🔴 建案 / 利冲 / 应收 / 分润 各自独立 save，无事务包裹。任一步 catch 仅记日志、不回滚前序写库 → 留下"有案无应收 / 有案无分润"的不一致态（只有步骤3整段发起失败才整体清理）

③ 办案：案件 → SOP/任务 → 文书 → 成本 → 预警 → 结案

角色：办案律师/助理。重点隐患：SOP 任务实例化函数无人调用（空壳），状态流转零校验，文书是模板拼装非真 AI。

步骤1 · 案件创建（B端）case.service.create
◈ 判断：!organizationId → BadRequest 缺少组织信息
无必填字段校验（客户/案件名非强制）；create 内无自动分配律师（独立接口，无人分配不报错）；利冲/类案/SOP 生成均 try/catch 静默
步骤2 · 办案 SOP / 任务实例化
⚠ generateTasksFromTemplate 无调用方（空壳）。真实路径是 createCaseSOP（创建案件时调用），按 case_type 读模板写 CaseTask。case.stage 变更不触发任务实例化 → 律师看不到随阶段推进的待办
步骤3 · 阶段/状态流转 updateStatus
◈ 判断：status===CLOSED → 走结案；其余状态 repository.update 无任何合法性校验 → 任意互转均放行
步骤4 · 文书生成 generateDocument
◈ 判断：模板缺失 → Error 模板不存在
⚠ 非真 LLM：仅 {{key}} 正则替换 / 字符串拼装（ai.service 未调用）。结案自动生成报告走 try/catch 静默
步骤5 · 案件成本 case-cost.service
◈ 判断（更新）：!existing → NotFound 成本记录不存在
create 事务内 save + 同步写 BusinessFund 支出；update 作废旧 fund+重写（静默 catch）；remove 删除后 fund 置 voided（静默）
◈ 角色：LAWYER / ASSISTANT 均可增删改，无细粒度区分
步骤6 · 预警（Cron 定时）
◈ 条件：仅对在办案件按 advanceDays[7,3,1] 生成；超期升级 URGENT
generateWarnings 每天0点 / checkOverdueWarnings 每小时 / checkOverdueReceivables 每天1点；失败均 try/catch 仅 logger.error；notify catch(e){} 吞错
步骤7 · 结案 closeCase
◈ 判断：结案不要求分润/应收完成，直接置 CLOSED；仅当 contract 应收 recvAmt≥totalAmt 时置 is_settled
分润：因需 status===CLOSED 才满足 → 实际靠结案触发（此处 catch 静默）。保全回写风险备注/预警失败均 catch(err){} 吞

④ 财务：收款 → 分润 → 对账 → 发票 → 代扣 → 退费

角色：财务。重点隐患：收款不写收支总账（收支割裂）、分润漏算协办、对账永不报错、发票/代扣/退费是状态壳。

步骤1 · 收款 recordPayment
◈ 判断：!amount||amount<=0 → 收款金额必须大于0；receivable 不存在 → 应收台账不存在
◈ 状态分支：newReceived≥合同额 → COMPLETED；>0 → PARTIAL；否则 PENDING
超额不报错、无重复收款校验；① 不写 BusinessFund（收支割裂）② 完成后触发分润 try/catch 吞 ③ 审计失败静默
步骤2 · 分润 checkAndTriggerCommission
◈ 判断：status!==CLOSED → skipped；receivable!==COMPLETED → skipped；已存在 → skipped
◈ 计算：要求 CLOSED 否则 案件未结案；COMPLETED 否则 款项未结清；基数仅 fee_amount（非实收）
⚠ 参与者仅主办律师（TODO：协办/邀约/谈案岗未实现）→ 其余角色分不到钱
步骤3 · 对账 runReconciliation
◈ 判断：逐笔遍历 receivable 计 match/mismatch；paymentRecord 总额与 received 差额>0.01 追加 mismatch；作废/冲红发票各追加
状态恒置 COMPLETED；payment 汇总异常、发票查询异常均静默 → 对账不一致永不报错，仅 mismatch_count 计数
步骤4 · 发票 create / issue
税率默认 0.06；状态默认 ISSUED；无真实税控/第三方通道（全壳，纯 DB 写入）；issueInvoice 仅改状态，无外部调用、无失败分支
步骤5 · 代扣 executeWithholding
◈ 判断：记录不存在 → 代扣记录不存在；status!==PENDING → 仅待代扣状态的记录可以执行
无 @Cron（仅手动）；无真实网关；成功后置 COMPLETED + 写 BusinessFund expense → "扣款"为伪操作，仅改状态+插支出；批量异常转 FAILED 记原因
步骤6 · 退费 payRefund
◈ 判断：审核 PENDING→APPROVED 回减 receivable（received 钳0、无余额上限）；payRefund 要求 status!==APPROVED → 仅已审核通过的退费记录可以打款；不存在 → 退费记录不存在
打款不真实：仅 PENDING→PAID 改状态，无银行出款、无失败分支 → 账实不符
步骤7 · 单案利润 getProjectRevenueOverview
◈ 计算：net_profit = BusinessFund 收入 − BusinessFund 支出
⚠ 注释称"含 case_cost"但代码未查 case_cost 表 → 成本漏算；因步骤1 不写 BusinessFund 收入 → 收入侧也失真（无报错）

⑤ 合规投诉 + 客户端回流

角色：客户(C端) / 合规岗。本期不做 C 端支付（已标注）。

步骤1 · C端投诉提交 createComplaint
◈ 判断：TS 层 type/client_id/... 必填，但 service 层无任何必填校验直接落库；case_id 可选（可无关联案件提交）
source_channel 不透传，后端硬编码 CLIENT_PORTAL；工单同步 try/catch 失败仅 console.error → "投诉成功但工单可能未进 B端"
⚠ 类型不一致：前端 service_quality/progress/fee_issue/other vs 后端 service_attitude/case_progress…（as any 原样入库 → 标签回落"其他"）；上传凭证 POST /upload 后端无路由 → 404，catch 后提示"上传失败，请重试"，降级为无凭证
步骤2 · B端工单三来源
◈ 来源：① C端提交同步（CLIENT_PORTAL）② 手动建单（必填 source_channel/type/severity/title/content）③ 低分评价自动建单（type=low_score_rating, HIGH）
权限：compliance.controller 无 CLIENT 角色 → C端不可访问 B端工单
步骤3 · 工单流转 / 升级
◈ 状态：PENDING→PROCESSING(assign)→RESOLVED→CLOSED(归档)/ESCALATED
ticket 不存在 → return null 不抛错（前端易拿 null 异常）；escalate 任意状态可调用无前置校验
步骤4 · 投诉率看板 getComplaintRateStats
◈ 判断：totalCases=0 → 投诉案件率=0；count=0 → 解决率=0；仅当被投诉案件非空才查 receivables，否则金额恒 0；无 receivables → COALESCE 兜底 0
by_source / by_type 缺省 other
步骤5 · C端案件查看
◈ 判断：/client/cases 按 client_id 查（无越权判断），空 → 前端"暂无案件"；/client/cases/:id：!caseEntity || client_id!==clientId → NotFound 案件不存在（统一 404 防泄露，无权限等同不存在）
步骤6 · C端签约预填 SignPrefill
◈ 判断：findSigning 不存在 → 签约记录不存在或无权访问；无 fadada_sign_task_id → 该签约尚未完成发起，缺少签署任务ID；法大大异常 → BadRequest(签约失败)
必填仅前端 field.required 驱动，后端不二次校验；提交后 status REVIEWING，返回 sign_url 进法大大签署页
步骤7 · C端归档 ClientArchive
◈ 判断：前端 file 必填（message.error）；无 file_url 时提示"文件暂无可下载地址"
⚠ file_url 写死 /uploads/archives/.. 后端原样存，无真实落盘 → 下载路径不存在 404；C端 client_archives 与 B端 case_archives 两张独立表、互不相通
步骤8 · C端支付 / 付款
🚫 本期不做（按你的要求暂不涉及）。注：此前审计发现该路径存在 403 阻断，但因本期不排期，图中略去。
