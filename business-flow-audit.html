三、必须修复的关键断点（一期上线前）

  • 🔴 C 端自助付费主流程断裂：Payment.tsx:154 直连 /finance/fee 与 /cases，二者 @Roles 均不含 CLIENT → 被 403。应改走 /client 专用接口，由 client.service 内部调 finance.recordPayment 并写 receivable/payment_record（若一期要开放 C 端支付）。
  • 🔴 分润「签约即算」为假触发：fadada.service:1596 在签约瞬间调 checkAndTriggerCommission，但强制 CLOSED+应收COMPLETED 永远不满足（commission.service:323）→ 死代码。应删除或改为仅留痕，统一由「结案+应收完成」事件驱动。
  • 🔴 RBAC 守卫 allow-by-default：roles.guard.ts:36-38 无 @Roles 即放行 → 漏标装饰器即越权。一期安全 P0，改为 deny-by-default。
  • 🟠 活码与线索脱节：channel-tracking.service:52 只计数不建 lead，投放漏斗无法归因。
  • 🟠 邀约无外呼/短信：invite-task.service:33 仅站内通知，与「邀约即外呼」预期不符（需明确产品边界或接入 SmsService）。
  • 🟠 办案任务与案件阶段不联动：CaseTask 静态 stage_id，无随 Case.stage 推进自动激活；且 generateTasksFromTemplate 为死代码。
  • 🟠 谈案通过 client_id='pending' 占位：opportunity.service:434 未建真实客户档案，导致案件-客户关联虚挂。

四、依赖与架构优化空间（按优先级）

P0 安全与核心业务断点

  • RBAC deny-by-default：roles.guard.ts:36 改为无 @Roles 即 403；super_admin 仍需显式授权。
  • 打通 C 端支付/建案回流：新增 /client/pay、/client/case/create 专用接口（CLIENT 可见），内部调 finance.recordPayment+建案，写 receivable/payment_record，消除 403 死路。
  • 修复分润触发：删除签约即触发死代码，统一由「结案 + 应收 COMPLETED」事件驱动；补全多角色分润（commission.service:245 TODO）。

P1 解耦与一致性

  • 引入领域事件（EventEmitter2）：把 投诉→工单、支付→分润/推送、签约完成→案件状态、成本→财务 改为事件订阅，消除 forwardRef 同步紧耦合（fadada↔case/finance）。
  • 发合同建案事务边界：generateCaseFromContract 的建案+利冲+应收四处独立 save（fadada.service:1557/1562/1580/1596）无事务，存在部分态；建议 saga 或显式事务+补偿。
  • 收款补齐收支流水：recordPayment（finance.service:143）写 PaymentRecord+核销应收，但不写 BusinessFund，导致经营看板/单案利润与收支流水割裂；应在同一事件里写 business_funds。
  • 统一利润口径：getCaseProfitAnalysis / getProjectRevenueOverview / dashboard 三套口径不一致，且 dashboard.service:440 含 Math.random() 假利润率 → 移除随机值、收敛到单一聚合服务。

P2 数据归属与审计

  • 归档表统一：client-archive 与 case-archive/archive-volume 二表不互通，C 端归档 B 端不可见 → 合一或建关联视图。
  • 审计补齐：createComplaint、uploadArchive、签约预填、createFee 等关键写操作补 auditService.logAction（漏覆盖 6 类）。
  • 共享内核抽取：UserRole/Case/User/Organization 等被全模块 import，抽 shared-kernel 模块降低耦合。
  • 线索-客户关联：lead 无 client_id、ClientProfile 无 lead_id（仅 phone 隐式关联）→ 建真实外键，闭合「线索→客户」链路。

P2 外壳能力（二/三期，非一期阻断）

  • AI 文书 / 类案：ai.service 接真实 LLM；
  • 发票：接税控/第三方（航信/法大大）开票通道；
  • 代扣 / 退费：接真实支付网关 + @Cron 自动触发；
  • 对账：改逐笔勾对（payment↔invoice↔fund）+ 定时；
  • 活码归因、邀约外呼/短信、SOP 任务随阶段联动。
结论：主业务价值流（获客→线索→谈案→发合同→回调建案→利冲→应收→办案→结案分润）是通畅成立的；需要在一期前修复的是 6 个明确断点（尤其 C 端支付 403、分润假触发、RBAC opt-in 三处），并把 AI/发票/代扣/退费 等外壳明确标注为「演示版」以免对外承诺假能力。架构层面最高杠杆的优化是 引入领域事件解耦 + RBAC deny-by-default + 统一财务聚合口径。
